What I learned.

Where are the data, control and management planes in your network?

Data plane: the Linux bridges (s1, s2, s3) in Mininet, which forward the frames. Control plane: none. There is no controller or routing protocol; every address is configured statically. Management plane: topology.yaml and build_topo.py.

How did your switches learn which port leads to each host? Use your MAC table evidence.

When a ping starts, h1's ARP request reaches the switch. The switch reads the frame's source MAC address and learns which port it came in on. macs.txt shows s1 learning h1 on port 1, h2 on port 2, h3 and h4 on port 3 (towards s2), and h5 and h6 on port 4 (towards s3).

Week 1's 2 a.m. change on 40 switches: what would be different if those switches were described like your network?

The change would be one edit to one file, checked by a script before it reaches any switch. Mistakes are faster to find and fix with a separate checker than on 40 switches one by one.

What's the difference between your network's data model and its serialisation? Use YAML and JSON as the example.

YAML and JSON are two ways of writing the configurations. YAML is more readable and allows comments, but both build the same network.

Why is it better to catch bad data in check() than with pingall? What did IPv6 notice about a duplicate address that IPv4 didn't?

check() runs before anything is built, so it doesn't use any resources and saves time. pingall only finds problems after the network is running. IPv6 runs Duplicate Address Detection and marked h2's copy dadfailed while IPv4 accepted the duplicate without any warning.

What does your Git history give you that copying files into folders named topology-v2-final wouldn't?

Git keeps the full change history: what changed, when and why. I can compare or go back to any version, and it's always clear which version is current.
