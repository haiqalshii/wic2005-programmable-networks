What I learned

Describe your design: hypervisors, tenants, VNIs and addresses. Which tenants overlap, and why did you place each VM where you did?

The design uses cedar, maple and willow at 10.95.0.1, 10.95.0.2 and 10.95.0.3 on underlay 10.95.0.0/24. Research uses VNI 9510: res1 and res4 are on cedar, res2 is on maple, and res3 is on willow. Studio uses VNI 9520: art1 is on cedar, and art2 and art3 are on willow. Both tenants use 10.95.50.0/24, with .10 onward assigned in YAML order. Their MAC prefixes are 02:00:25:26:00 and 02:00:25:30:00 respectively. This placement exercises local switching, remote forwarding, shared hypervisors and three-way flooding.

Each hypervisor has a separate bridge and VXLAN interface for each resident tenant. A VXLAN device has a local underlay address and no fixed remote; its all-zero-MAC flood entries identify only the other hypervisors hosting that VNI. The underlay transports outer IPv4/UDP packets, while guest Ethernet and IP addresses remain inside the VXLAN payload. The final tenant MTU is 1500 and underlay MTU is 9000. Automated validation passes, including address, placement, unique MAC, bridge membership and flood-peer checks. Runtime packet delivery is unverified because Mininet is absent and Docker is unavailable; evidence files explicitly record these limitations.

Two of your VMs have the same IP address. Using your evidence, explain how a ping reaches the right one — and what would have to go wrong for one tenant to see another's traffic.

Research res2 and studio art2 both have address 10.95.50.11. Their MAC addresses differ: 02:00:25:26:00:0b and 02:00:25:30:00:0b. Res1's ARP request belongs to bridge br9510 and VXLAN VNI 9510, so it is replicated only to the research VTEPs. A reply from res2 should populate res1's neighbour table with the research MAC. Art1's independent ARP resolution should instead find the studio MAC over VNI 9520. Hypervisors maintain separate bridge forwarding domains, and receiving VTEPs demultiplex VXLAN traffic by VNI.

The isolation collector captures ARP/ICMP at art2 while res1 pings res2, then checks studio communication and neighbour tables. evidence6/isolation.txt contains a genuine dependency failure, not a zero-packet capture or a successful isolation result. Therefore isolation is supported by the validated configuration but has not been demonstrated experimentally here. Incorrect bridge membership, mapping both tenants into one VNI, or an intentionally connected tenant gateway could defeat the intended separation. VNI separation is not encryption or authentication; the underlay must also be trusted and controlled.

Using your evidence, explain what was flooded, to which hypervisors, and what each VTEP learned. With 50 hypervisors in one VNI, how many copies would one broadcast need — and how would EVPN change that?

Initially, each research VXLAN device has two static all-zero-MAC flood entries, one for each other research hypervisor. Studio devices have one remote flood entry each because studio occupies only cedar and willow. These entries are replication destinations, not learned guest MAC mappings. An initial research ARP broadcast from res1 should be copied from cedar to maple and willow; the collector captures at willow, which hosts neither of the communicating res1/res2 pair. Each receiving bridge can learn the source MAC on its VXLAN port, and the VXLAN FDB can associate that source MAC with the originating remote VTEP address. Replies allow cedar to learn the destination's remote mapping, enabling later unicast without unknown-destination flooding.

The before/after tables and packet trace remain unmeasured: evidence6/flood.txt records that Mininet could not be imported. They must not be interpreted as observed learning. With 50 hypervisors hosting one VNI, ingress replication sends 49 copies of one broadcast. EVPN advertises MAC/IP reachability and VTEP membership through BGP, allowing remote unicast forwarding entries to be installed through the control plane. ARP suppression can reduce address-resolution broadcasts, but EVPN does not eliminate all broadcast, unknown-unicast and multicast traffic.

Compare your two MTU fixes using your measurements. Which would you choose for a data centre, what does each cost, and who has to change what?

The original all-1500 design is preserved in blackhole.yaml. check_mtu() rejects both tenants because 1500 + 50 = 1550 exceeds the underlay by 50 bytes; evidence6/check.txt contains the actual diagnostics. IPv4 VXLAN adds 14 bytes of inner Ethernet, 8 VXLAN, 8 UDP and 20 outer IPv4. Outer Ethernet is outside the underlay IP MTU budget. IPv6 would replace the 20-byte outer header with 40 bytes, giving 70 bytes of overhead, but the assignment builder is IPv4-only.

The requested Fix A, tenant 1950 with underlay 1500, is not a valid fix: it exceeds the budget by 500 bytes. mtu_a.yaml intentionally preserves that specification and is rejected. The corrected reduced-MTU alternative is mtu_a_reduced.yaml, tenant 1450 with underlay 1500. Its IPv4 ICMP payload boundary is predicted to be 1422/1423 bytes because the inner IPv4 and ICMP headers total 28 bytes. Fix B, mtu_b.yaml, keeps tenant MTU 1500 and raises the underlay to 9000; its guest-interface boundary is predicted to be 1472/1473. Both corrected alternatives pass static validation. These are calculated boundaries, not observed ping outcomes.

A mismatch may allow small packets and TCP handshakes while dropping larger frames or full TCP segments. Inner DF does not by itself establish the outer fragmentation policy, and virtual links may show offload or receive-tolerance effects, so packet captures and drop-counter deltas are necessary. evidence6/blackhole.txt and evidence6/fixes.txt show blocked execution, with no measured maximum payload or receiver throughput. The seven-part lab's possible four-byte Linux receive tolerance is a hypothesis, not a result.

I select Fix B for a managed data-centre fabric: it preserves conventional guest MTU and provides encapsulation headroom, provided every underlay link supports the configured jumbo MTU. The reduced alternative avoids changing the fabric but requires every guest and tenant interface to use 1450, reducing per-packet payload. No measured performance advantage is claimed. Mininet throughput would also depend on CPU load, scheduling, packet rate and offload state, so actual receiver rates and retransmissions must be collected before comparing performance.

If your hypervisors' VTEPs were P4 switches running the lecture's vtep.p4, what would have to fill the vtep_encap table, and how? What would replace flood-and-learn?

The checkout and available history contain neither the Week 5 P4 tunnel nor the lecture's vtep.p4, so the exact vtep_encap match key, action parameters and previous tunnel header size cannot be verified. At a conceptual level, a controller or management program would need the same tenant membership and endpoint-location information expressed by overlay.yaml: which tenant/VNI owns a destination, its remote VTEP address and the underlay forwarding information. It could use P4Runtime or the lecture program's supported management API to install the corresponding match-action entries. The actual program must be inspected before claiming a particular table schema or issuing table writes.

An endpoint directory or EVPN-informed controller could distribute remote reachability and program the P4 VTEPs instead of discovering every remote MAC through flood-and-learn. It would also need to handle endpoint moves, withdraw stale mappings and define replication for unresolved broadcast/multicast traffic. VXLAN adds 50 bytes for IPv4 or 70 for IPv6 beyond an inner IP packet; only the VTEPs need to understand VXLAN, while the transit fabric forwards the outer IP packet. A custom P4 tunnel requires its encapsulating and decapsulating P4 devices to understand its custom headers; the transit requirements and numeric overhead depend on the missing implementation. Loop prevention similarly depends on that program. In this design there is one logical VXLAN bridge port per tenant at each hypervisor and no local bridge cycle; normal bridge forwarding does not send a received frame back out the same VXLAN port. A loop-free underlay and consistent tenant attachment remain necessary; VXLAN itself is not a universal loop-prevention protocol.
